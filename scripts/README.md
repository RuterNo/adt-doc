# AsyncAPI Schema Generator and Validator

A developer tool to validate message schemas, verify example payloads, enforce consistent metadata and documentation, and generate a complete AsyncAPI specification.

This tool focuses on formatting and structure validation only — not business logic, MQTT semantics, or runtime message behavior.

---

## Project File Layout

Each message must include a set of files with a defined structure and naming convention:

| File Type         | Description                                                  |
|------------------|--------------------------------------------------------------|
| `*.json`         | JSON Schema Draft-07 defining the message payload            |
| `*.meta.json`    | Metadata file describing message usage and topic parameters  |
| `*.md`           | Markdown documentation with a metadata summary table         |
| `*_example.json` | One or more example files with a `payload` object            |
| `asyncapi.yml`   | The output file generated or updated by this tool            |

```bash
source adtdoc-venv/bin/activate
```

### Step 3: Install dependencies
```bash
pip install -r requirements.txt
```

## How to Use

Run the script:

```bash
python asyncapi_generate.py
```

This will:

- Validate all JSON schemas
- Validate example payloads against schemas
- Auto-generate missing metadata (if enabled)
- Update Markdown documentation
- Update `asyncapi.yml`

---

## Configuration Flags (inside the script)

You can configure behavior at the top of `asyncapi_generate.py`.

### WRITE_CHANGES_TO_ASYNC_API_YML

Determines whether changes are written to `asyncapi.yml` or printed to stdout:

```python
WRITE_CHANGES_TO_ASYNC_API_YML = True  # Set to False for dry-run mode
```

### CREATE_META_IF_MISSING

Optionally create `.meta.json` files if they are missing:

```python
CREATE_META_IF_MISSING = False  # Set to True to generate placeholder metadata
```

## Example Workflow

1. Add or edit a schema in: `asyncapi/json-schemas/[channel]/[name].json`
2. Add at least one example file: `*_example.json`
3. Add a `.meta.json` file for the schema (or let the tool create one)
4. Add a `.md` file with a required summary table
5. Run the script
6. Review and commit changes to `asyncapi.yml`

## File Formatting Requirements

### Schema File (`*.json`)

- Must follow JSON Schema Draft-07
- Required fields:
    - `$id` (auto-generated)
    - `$schema`
    - `title` (derived from file name)
- All fields in `required` must be defined in `properties`

### Metadata File (`*.meta.json`)

- Required fields:
    - `mode`: `"publish"` or `"subscribe"`
    - `mqtt`: includes `qos`, `retain`, and optional `params`
    - `maintainers`, `producers`, `consumers`
    - `service-level`
- `topic` is auto-generated by the tool

### Documentation File (`*.md`)

- Must include a Markdown table with the following fields:
    - Maintainer
    - Central Topic
    - Schema
    - Producer
    - Consumer
    - Service Level

> The script will update the values in this table. It will not add missing rows.

### Example Files (`*_example.json`)

- Must contain a `payload` key with valid data
- Payload must validate against the schema

## Troubleshooting

> **Missing metadata file**  
Set `CREATE_META_IF_MISSING = True`, or add a `.meta.json` file manually.

> **Invalid example file**  
Ensure the `payload` section in the example matches the schema.

> **Missing documentation rows**  
Manually add the expected table rows. The script will only update existing ones.

> **Conflicting or missing `$id`**  
Ensure every schema has a unique `$id` and follows the standard format.

---

## Scope and Limitations

This tool:

- Validates formatting and schema consistency only
- Does not interpret MQTT behavior or business semantics
- Does not generate missing documentation — only updates existing content
- Should be used alongside source control to track changes
